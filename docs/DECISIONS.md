# Project Decisions

All former open questions are now decided. D-01 and D-18 were decided by the product owner; the rest were decided by the development team
under the owner's instruction ("use your capabilities to solve them"). A decision changes only if the owner asks.

| # | Topic | Decision | Rationale | Affects |
|---|---|---|---|---|
| D-01 | **Multiple schools** | One platform serves **many schools**. Each school has its own users, roles, data, settings, documents and website; school users never see other schools. Shared DB with `school_id` + PostgreSQL RLS (ARCHITECTURE §4.0). Sign-in = school code + username + password | **Owner decision.** Shared schema is cheapest on Railway and simplest to migrate; RLS gives database-level isolation | All |
| D-01a | **Super admin = system owner** | The super admin is **the product owner of the whole system**, not a school user. The super admin has **full access to all schools' details and data**: an all-schools overview with key figures and cross-school reports, one-click switching into any school with every module and permission (view and edit), plus school management (create/suspend schools, domains, school admins and users, audit logs, exports). All actions are audited. Mandatory TOTP | **Owner decision** | All |
| D-02 | UI library | **shadcn/ui** + Tailwind (Radix primitives) | Accessible, fully customisable, no runtime theme lock-in | Frontend |
| D-03 | Legacy data migration | Reusable per-school **CSV/Excel importer** with validation + reconciliation report. Imported: active students, families/guardians, staff, classes/sections, **opening fee balance per student** at cut-over, and the last 2 years of exam results. Older history is attached as archived PDF/Excel files on the school record | Full-history migration from an un-inspected system is high-risk; balances and current records are what daily work needs | Phase 2 (formats), 11 |
| D-04 | Payroll | **Basic payroll**: salary profile with increments; monthly sheet from approved staff attendance; deductions per settings (absent, half-day, late-as-absent, extra leave); tax as a manual per-staff amount; approve → pay → journal posting; salary slip PDF | FR references it in 6.8/12/13.12; full tax computation is out of scope | Phase 4 |
| D-05 | Accounting depth | Internal **double-entry journal**, invisible to users (simple income/expense/transfer screens). Balance sheet report = S priority | Guarantees fee income is counted once and the books always balance | Phase 3–4 |
| D-06 | SMS / WhatsApp | Provider-agnostic `MessageProvider` port. **SMS first** through one platform-level gateway account (a Pakistani bulk-SMS gateway with an HTTP API, selected when the account is opened); each school sets its own sender mask; messages metered per school for billing. **WhatsApp** (Meta Cloud API) after go-live. Email via SMTP for password resets | One integration serves all schools; costs traceable per school | Phase 1 (OTP), 7 |
| D-07 | PDF engine | **OpenPDF** only (JasperReports not used). English only, embedded fonts | Urdu removed, so no complex shaping needed; OpenPDF is lighter | Phase 0+ |
| D-08 | Printing | Fee voucher: A4 with 3 copies (bank / school / parent). Receipt: A5. Thermal receipts not in v1 | Matches common Pakistani school practice; works on any laser printer | Phase 3 |
| D-09 | Attendance % | `% = (Present + Late + 0.5 × HalfDay) ÷ (WorkingDays − ApprovedLeaveDays) × 100`, rounded to 1 dp. Holidays/OFF days are never working days. A per-school setting can make Late count as absent after N lates (default off) | Clear, common and testable (QA-ATT-006) | Phase 5 |
| D-10 | Two-factor auth | Super admin: TOTP **mandatory**. School users: step-up OTP required for sensitive screens; sign-in TOTP optional per user, and each school can make it mandatory for admin/principal/accountant | Balances security with ease for teachers | Phase 1 |
| D-11 | Antivirus on uploads | Not in v1. Strict size/magic-byte checks, private storage, download-only (never inline) | Cost vs. risk for school documents/photos | Phase 2 |
| D-12 | Timetable / daily diary | Timetable = S (FR 6.4). Teacher daily diary is **not in v1** (mentioned but never described in the FR) | Keeps scope to described features | Phase 2 |
| D-13 | Extra roles | Seed **SCHOOL_OWNER** (a school's proprietor/director, inside one school only, not the system owner: read-only finance + reports + dashboard) and **AUDITOR** (read-only finance + audit log) roles in every school | FR 10.17 "owner", FR 10.18 "auditors" | Phase 1 |
| D-14 | Grading details | Percentage computed to 2 dp; band lower bound inclusive (95.00 = A++). Positions: standard competition ranking (1, 1, 3). Cumulative result: per-exam weights, default equal. All configurable per school | Deterministic and testable (QA-EXM-005/007/012) | Phase 6 |
| D-15 | Document designs | 2 report-card layouts, 1 design per certificate type, 1 voucher, 1 receipt. Each school customises via its document identity (logo, letterhead, stamp, signatures) and layout options in settings | Serves many schools without bespoke work | Phase 2, 3, 6 |
| D-16 | Bank details / bank payments | Bank name, account title and number come from school settings and are printed on vouchers. Bank-paid vouchers are entered manually by the accountant (no bank file import in v1) | No bank integration specified | Phase 3 |
| D-17 | Accounts and domains | SelectCode owns the Vercel, Railway and Cloudflare accounts (it is the platform operator). Platform domain is written as `<platform>` in the docs until registered. Schools bring their own website domain (or use `<code>.sites.<platform>.com`) | Multi-school SaaS needs one operator | Phase 0 |
| D-18 | **Language** | **English only, permanently.** No Urdu, no RTL, no i18n framework, in UI, PDFs, SMS or website. FR references to Urdu (4.3, 10.16) are dropped | **Owner decision.** Avoids rendering/shaping issues | All |
| D-19 | **Parent and student portals** | **Removed.** No parent or student logins, portal or app. FR 8.7 is out of scope. Parents are informed by SMS (receipts, attendance, results, reminders) and printed vouchers/report cards. Leave applications are entered by office staff (FR 13.8) | **Owner decision** | All |
| D-20 | Mobile | Staff portal is responsive (usable on tablets); no mobile app | Follows D-19 | Frontend |
| D-22 | **Source control** | **No GitHub** (or any hosted git). Local git repository only, no remote. Quality checks run locally with `scripts/verify.sh`; deploys use the Railway and Vercel CLIs; dependency updates are reviewed monthly by hand; the repository is backed up as a `git bundle` to private R2 storage each release | **Owner decision** | All |
| D-23 | Step-up channel | Step-up codes are 6-digit, emailed, valid 5 minutes (5 tries); a verified step-up lasts 15 minutes in the session and is cleared when the super admin switches school. Users without an email cannot do step-up actions | Works without an SMS provider; SMS can be added in Phase 7 | Phase 1 |
| D-24 | Audit writing | Application services call `AuditService.record(...)` explicitly inside their transaction (instead of an automatic aspect), so each entry has a meaningful action name, before/after values and reason | Clearer, testable history | All |
| D-25 | Single backend instance in v1 | Rate limits and the settings cache are in memory per instance. Before running more than one backend instance, move them to the database or a shared cache | Simplicity; one instance is enough for v1 load | Phase 10 |
| D-26 | Super admin new-school flow | The new school's ID is reserved first, then the school row, profile, built-in roles and main administrator are created in one transaction already running as that school (RLS) | Atomic: no half-created schools | Phase 1 |
| D-27 | Enrolment needs approval | An enquiry can be enrolled only after its status is "Admission approved"; the Enrol button stays disabled with a hint until then | FR 4.6 speaks of converting an *approved* enquiry; stops accidental enrolments | Phase 2 |
| D-28 | Sign-in bookkeeping | Failed-attempt count, lock and last sign-in are written with single atomic SQL updates, not through the versioned user entity | Two devices signing in at once must both work, and signing in must not cause a false "changed by someone else" for an admin editing the user | Phase 2 |
| D-29 | PDF output | Certificates, forms, bio-data and ID cards are generated on the server and downloaded as a PDF file (not opened in a pop-up tab) | Browsers block pop-ups opened after a request finishes; a download always works and the file can be printed or kept | Phase 2 |
| D-30 | Private fields on edit | When a role cannot see private fields (contacts, CNIC, B-Form, address), they are hidden in forms and the server keeps the stored values on save | Hiding must never turn into deleting | Phase 2 |
| D-31 | Bill runs without Spring Batch | Bill and late-fee runs are a plain service: a `fee_run` row keyed by the Idempotency-Key, students processed in chunks of 50 (one transaction each), and a database rule that a student is never charged the same head for the same period twice. A run stopped half-way is finished by running it again. Spring Batch can be added later if runs need scheduling or partitioning | The same guarantees (restartable, idempotent, no duplicates) with no framework and no batch metadata tables; school-sized runs finish in seconds | Phase 3 |
| D-32 | Balances are computed, money is insert-only | Line balance = net + approved corrections − allocations, read through `security_invoker` views so row-level security still applies. The app role can only INSERT bills, lines, payments, allocations, corrections and journal lines; approvals are separate rows | Nothing can be edited in place; every figure can be traced (FR 10.18) | Phase 3 |
| D-33 | Advance credit = unused part of payments | No separate credit table: credit is what a payment has not yet settled. Using it later adds a CREDIT allocation (journal Dr advances / Cr fee income). A charge reduced after payment releases the excess back to credit (RELEASE allocation) instead of being refused | One balance formula for everything; payments = allocations + credit always reconciles | Phase 3 |
| D-34 | One family at a time | Payments, bill runs, credit use and corrections take a PostgreSQL advisory lock on the family for their transaction; requests with the same Idempotency-Key also lock on the key | Two cashiers can never settle the same fee twice, without needing UPDATE rights on money tables | Phase 3 |
| D-35 | Message outbox now, messaging module later | Receipt and reminder SMS are written to `message_outbox` in the same transaction and sent by a background dispatcher with back-off (5 tries), visible in the fee message log. Phase 7 adds providers, templates and other channels on top | A provider outage never blocks or undoes a payment (QA-FEE-015) | Phase 3 |
| D-36 | Payroll before attendance | Until Phase 5 the absent, half, late and leave days are typed on the draft salary sheet. Payroll already asks a `StaffAttendanceSummary` hook for approved monthly totals; Phase 5 implements it and the sheet fills itself (lines show where the figures came from) | Payroll is usable now without waiting for attendance | Phase 4–5 |
| D-37 | One journal writer | Fees, accounts and payroll post through `shared/accounting/JournalWriter`: balanced entries only, cash/bank accounts locked per transaction, and nothing dated on or before a closed day for that account (fee receipts included) | One set of rules for all money; a closed day really stays closed | Phase 4 |
| D-38 | Salary month rules | A month uses the salary record in effect on the 1st (a mid-month increment applies from the next month). Per-day rate = basic ÷ working days of the month from the school calendar; the deduction is rounded once (HALF_UP). Approval posts Dr salaries / Cr salaries payable, tax payable and salary deductions; payment posts Dr salaries payable / Cr cash or bank | Simple, predictable payroll that staff can check on the slip | Phase 4 |
| D-39 | Categories are ledger accounts | Each income or expense category has its own ledger account (codes 41xx/51xx), so reports by category come straight from the journal; the "Salaries" category is reserved for payroll | Reports always match the books (QA-ACC-008) | Phase 4 |
| D-40 | Approval of large expenses | Expenses, supplier bills and supplier payments above the school's limit (Rules & settings, default Rs. 50,000) wait for someone with the approval permission; their own entries are approved at once and recorded as such. Income and transfers need no approval | Matches FR 11.5 without slowing daily work | Phase 4 |
| D-41 | Who takes a register | Users with the "all classes" scope take any register; teachers take only sections where they are class teacher on that date and see the sections they teach. Earlier days and closed days are changed only with the correction permission and a reason | Matches school practice; every change after the day is accountable | Phase 5 |
| D-42 | Attendance % base | D-09 is applied to working days that have a mark; a working day whose register was not taken is left out of the percentage and shows in the missing-register list instead | A forgotten register never makes a child look absent | Phase 5 |
| D-43 | Fixed attendance codes | P, L, HD, A, LV (D-09) are fixed codes rather than a school-edited list; holidays are days off in the calendar, never a status | The percentage formula depends on what each code means | Phase 5 |
| D-44 | Staff month approval | Payroll uses only an approved staff month. Approval needs every day marked, or "count days not marked as present"; an approved month cannot be changed until reopened, and reopening is refused once salaries for the month are approved | Salaries are always based on figures someone signed off | Phase 5 |
| D-45 | Absence SMS and late arrival | Absence SMS is off by default (setting) and sent once per child per day, only for the same day's register. Student arrival times use the first student late time; the second slot is kept for later use | Avoids unwanted messages and cost; simple first version | Phase 5 |
| D-46 | Who is in a class for an exam | Students and their sections are taken as on the exam's last day (or today, if the exam is not over), inside the academic year. Marks are entered per paper and section; teachers enter only the subjects they teach in that section, and see results only for sections they teach | A child who moves section mid-term appears once, in the section they sat the exam in | Phase 6 |
| D-47 | Absent, exempt and grade-only classes | Absent counts as 0 and fails the paper; Exempt leaves the paper out of the total; an empty box is a missing mark and blocks publishing. Grade-only classes (early years) record a grade per paper with no totals, percentages or positions; the child passes when every grade is a passing grade | The office can tell "not marked yet" from "did not sit" | Phase 6 |
| D-48 | Positions | When the school shows positions (setting), students are ranked by percentage across the whole class (all sections), only if all their marks are entered. Ties follow the setting: 1, 1, 3 (standard) or 1, 1, 2 (dense) | Incomplete results never push other students down | Phase 6 |
| D-49 | Publishing and corrections | Publishing a reviewed class freezes a snapshot of each student's result (marks, grade, position, remarks, attendance %) as a numbered version. Report cards, result sheets and SMS use the latest snapshot, so later changes to grade scales or settings do not alter them. Correcting needs the unlock permission, a verification code and a reason; each mark changed afterwards is logged with that reason, and publishing again adds a new version while old versions are kept | Published results are a record; any change is visible and explained | Phase 6 |
| D-50 | Remarks, admit cards and result SMS | Teachers write the class teacher's remark for sections they teach; the principal's remark needs the review permission. Holding back admit cards for overdue fees is a choice made at printing, not a rule. Result SMS go only for published results, once per student per send (brothers and sisters on one phone each get their own) | Keeps fee pressure a school decision and avoids duplicate messages | Phase 6 |
| D-51 | Simple test marks replace exam screens | By the owner's decision (2026-10-31), schools record marks without creating exams: a test is one subject of one section on one day, with an "out of" total. Positions come per test and overall over a period, using the school's tie rule. Absent counts as 0 overall and has no position in that test; a student is ranked overall on the tests they have marks in, and the list shows how many they took. Changing a saved mark needs a reason and is logged. The exam, datesheet, publishing and report card features (D-46…D-50) stay in the code and API but are not in the menu, so they can return | The school wants marks and positions, not an exam workflow | Phase 6 |
| D-52 | Dashboard is one role-filtered response | One `GET /dashboard` builds only the panels the user's permissions and data scope allow; panels not allowed are absent from the response. No 60-second cache for now: figures stay current, and a cache is added only if the load-time target is missed | Simpler than one endpoint per panel, and security is decided in one place | Phase 7 |
| D-53 | Urgent lines | At most five, in this order: attendance not entered (each class if one or two, otherwise a count), staff attendance not entered, complaints open too long, enquiries with no follow-up, fee follow-ups overdue, overdue tasks. The day limits are settings (7 and 3 days). Nothing about attendance on a day off | Matches FR 3.13 without cluttering the screen | Phase 7 |
| D-54 | Masking figures | With the setting on, totals and fee figures are left out of the response until the user presses Show figures, which lasts until the page is left | Figures cannot be read from the screen or the network tab by a passer-by | Phase 7 |
| D-55 | Messages | Bulk SMS shows recipients, parts and estimated cost before sending; one message per phone per send, so brothers and sisters do not cost twice. Automatic messages use templates a school may reword, and every template message ends with the school's message signature. Welcome messages go once per student and birthday wishes once per person a year. The SMS gateway is configured by a URL template, since the account is not opened yet; staging sends only to an allow-list. WhatsApp stays after go-live (D-06) | Keeps costs visible and one integration for all schools | Phase 7 |
| D-56 | Circulars and tasks | Circulars are for staff; families are told through Messages, since there is no portal. A task is seen by its creator and the people it is shared with, and any of them can complete it. Calendar holidays are for information; days closed for attendance stay under Academic years | One meaning for each list | Phase 7 |
| D-57 | One report object | Each report is built once as a `ReportDoc`, then drawn on screen, in the PDF and in Excel, so values cannot differ and a section left out for a role is missing everywhere. Money and percentages are numeric cells in Excel | QA-RPT-003 and QA-RPT-004 hold by construction | Phase 8 |
| D-58 | Report periods | Dates must be inside the selected academic year. The comparison period is the previous calendar month for a whole month, otherwise the same number of days just before, cut off at the start of the year. Weeks run Monday to Sunday | Years never mix (FR 15.1) | Phase 8 |
| D-59 | Who sees which report | Student and class reports need the reports permission; teachers get only sections they teach. Teacher reports need their own permission and the "all classes" scope. Fee figures appear only with fee access and the "all classes" scope. Conduct is not in the student report because the system records none | Matches FR 15.7 | Phase 8 |
| D-60 | Marks on time | Test marks count as on time when every student in the section has a mark and the first entry of the last mark is within a set number of days of the test (setting, default 7). Corrections do not make a test late. Marks are credited to the teacher assigned to that subject and section on the test date, whoever typed them | Teacher reports stay fair; the system does not track who should have typed each mark | Phase 8 |
| D-61 | Exporting detailed reports | Existing report pages get Excel, PDF and Print through one bar that sends the tables and filters shown on screen to the server to turn into a file. It reads nothing from the database, so it cannot reveal more than the user already sees. Every export is audited | One way to export, without rewriting each report | Phase 8 |
| D-62 | Cross-school figures | Compared for any dates: students at the end date, attendance %, billed, collected, income, expense, test average; outstanding and defaulter families are as of today. Totals come from the underlying figures, not from averaging each school's percentage. Each school's academic year may differ, so this report is not limited to one year. Hidden exam results are not in the test average | Honest totals across schools (P-9) | Phase 8 |
| D-63 | No public website | **Owner decision (2026-10-31).** Phase 9 is dropped: schools get no public website, and FR 16.1–16.11, the website form counters (FR 3.2) and website pages for P-6 are out of scope. Domain mapping and the `site/[host]` route from Phase 1 stay in the code, unused. Online enquiries are not offered; staff enter enquiries themselves | The school does not need it | Phase 9 |
| D-21 | Online fee payment | Deferred (FR 10.19 = C). The payment-provider port is designed in Phase 3 so it can be added later (it would use a payment link sent by SMS, since there is no portal) | FR marks it as a future option | Later |
